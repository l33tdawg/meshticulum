# Experimental forward-private sessions

[`forward_session.py`](../src/meshticulum/privacy/forward_session.py) is an experimental end-to-end session primitive for the existing private envelope. Its v2 design uses dedicated Noise X25519 static keys, fresh interactive key agreement and Ed25519-signed key confirmation around an unchanged LM1/LM2 sealed record. It has source fixtures and a reference-vector comparison, not native deployment or radio qualification. The ordinary [radio](../src/meshticulum/bench/wire.py), [IP](../src/meshticulum/ip/wire.py) and [static recipient envelope](../src/meshticulum/privacy/mesh_envelope.py) modes retain their existing properties; this module does not upgrade them automatically.

The frozen MT05 flow is unchanged. Meshticulum provides this generic primitive; [Lantern](https://github.com/l33tdawg/sage-lantern) owns native identity storage, private policy, capture, consent, provisioning and deployment. The dependency remains Lantern → Meshticulum. Both repositories remain private, and this work creates no device authority or release.

## Intended protection and assumptions

The intended protection is against later decryption of captured **outer session records** after long-term signing or Noise static keys are compromised. It depends on fresh secure ephemeral keys, a completed authenticated exchange, protected session keys and effective destruction of ephemeral/session secrets. It does not protect a compromised live endpoint or erase private content that an endpoint has already stored.

The existing inner SealedBox record still uses a static recipient key. If that inner record is captured or retained separately, later recipient-key compromise can expose it. Wrapping it in a forward-private session does not change its storage properties. Native capture and staging must distinguish outer network records, inner sealed records and admitted application content. [SealedBox construction](https://doc.libsodium.org/public-key_cryptography/sealed_boxes)

The caller independently pins both complete Ed25519 peers and their two dedicated Noise public keys. An opaque `binding_digest` must represent the approved application context; the primitive cannot establish that digest's meaning or decide whether the peer is authorized to send a particular message. A trusted clock, live authorization and durable counter implementation are also caller responsibilities. No certificate enrollment, discovery or trust-on-first-use is supplied.

## Dedicated key boundaries

`ForwardContext` requires two distinct, canonical 32-byte Noise public keys. It rejects either role's key if it equals either pinned peer's known Ed25519-to-X25519 legacy recipient key. Canonical encoding checks also reject zero and noncanonical field encodings. The constructor requires a separate `noise_static_key` whose public key matches the local Noise pin before calling authority or claiming state. It never converts the signing private key for the Noise exchange; public-key conversion is used only to detect the two known legacy keys.

The caller must generate Noise keys independently with a secure random source, assign them a dedicated purpose, authenticate their association with the pinned signing identity, and protect their storage, rotation and retirement. Equality checks against two known legacy keys cannot prove independent generation, exclude reuse with other identities/protocols, or attest a key's provenance. Canonical encoding is not a key-origin or lifecycle guarantee. The public deterministic keys in the [v2 reference fixture](../tests/fixtures/noise-kk-vector.json) establish no native generation evidence.

## Exchange and record boundaries

The key agreement uses `Noise_KK_25519_ChaChaPoly_SHA256`. Both dedicated Noise static public keys are known before the exchange. The ordered signing peers, both Noise public keys, session ID, application binding, original epoch lifetime and record limit are hashed into the v2 prologue. Local role also binds the counter claim and signed confirmation. Fresh X25519 ephemeral keys contribute to the final directional keys. The token order and split follow the [Noise specification](https://noiseprotocol.org/noise.html#interactive-handshake-patterns-fundamental).

| Phase | Initiator | Responder | Application availability |
| --- | --- | --- | --- |
| H1 | `start()` creates the first empty-payload handshake message; state becomes `await_h2`. | `respond()` authenticates H1, creates H2 and derives keys; state becomes `await_confirm_i`. | No application records. |
| H2 | `finish()` authenticates H2 and derives keys; state becomes `send_confirm_i`. | Waits for initiator confirmation. | No application records. |
| Initiator confirmation | `confirm()` encrypts an Ed25519-signed context/transcript/role digest; state becomes `await_confirm_r`. | `accept_confirmation()` verifies that digest and signature, commits replay acceptance and produces its encrypted signed reply. | Responder becomes locally `ready` after producing the reply. |
| Responder confirmation | `verify_confirmation()` authenticates the reply and commits replay acceptance; state becomes `ready`. | Already locally `ready`. | Each endpoint may use its ready session. The caller must deliver confirmation before dependent application records. |

Empty handshake payloads carry no legacy private content. The additional confirmations bind both dedicated Noise public keys to the full Ed25519 peers, application context, role and final handshake transcript. A locally ready responder has verified the initiator and produced its own confirmation; it has no proof that the initiator received that reply. Reliable delivery, ordering, retransmission and application receipts remain separate integration duties.

`MPF2` is Meshticulum's separate v2 framing and record protocol. Its 29-byte header contains magic, message kind, session ID and counter. Encrypted confirmation and DATA records authenticate the v2 `DOMAIN + header` as associated data. Counter 1 is reserved for confirmation in each direction; DATA starts at 2. The record nonce is four zero bytes followed by the little-endian encoding of `counter - 1`. The bounded context permits at most 4,096 counter values per direction, including confirmation and consumed reservations. The parser rejects MPF1; there is no v1 or plaintext fallback.

Each handshake packet is 77 bytes; each confirmation is 141 bytes. DATA adds 45 bytes to the unchanged binary envelope and remains bounded by its existing size ceiling. These are encoding sizes, not measured link costs. The Noise handshake bodies, MPF2 framing, signed confirmations and LM1/LM2 records form a project-specific composition; an ordinary Noise or NoiseSocket peer is not wire-compatible with this service.

## Durable state, deadlines and failure

One session belongs to one process/thread owner and one incarnation. The caller supplies a counter store with three required synchronous operations; commit receive mode adds a fourth:

- `claim(binding)` must durably and uniquely claim the session ID and local role in a dedicated namespace. Its key is independent of the remaining context, so changing peers, expiry or limits cannot reclaim that ID/role. Reuse must fail, including after restart. The full context is authenticated separately by the prologue and signed confirmation.
- `reserve_transmit()` must commit a new monotonically increasing counter before returning it. Encryption happens afterward. A lost result or later encoding failure leaves the reservation consumed.
- `record_receive(counter)` must durably commit replay acceptance for confirmations and, in return mode, DATA before opened bytes are returned. A lost result fences the session; a committed acceptance remains committed.
- In commit mode, `commit_receive(candidate)` must atomically create DATA replay acceptance and exact recoverable sealed bytes in the same claimed namespace, after validating the original prepared intention. Core requires this callback before claiming a commit-mode session but cannot prove the provider's transaction or native authority.

The record/prologue domain changes to v2, but `COUNTER_CLAIM_DOMAIN` deliberately preserves the exact retired v1 session-ID/local-role claim hash. In the same protected namespace, upgrading cannot reclaim an ID/role already recorded under that v1 scheme. A caller must retain existing claims rather than create a fresh store to bypass them. This is a source compatibility control, not proof of native migration or rollback resistance.

These counters are independent of adjacent-link flow counters and radio/IP debt. They do not replace application replay admission or refund transport attempts. Native transaction durability, protected file ownership, deletion/rollback resistance and recovery of uncertain writes remain unqualified here.

Operations check live authorization, the original epoch window and the caller's original monotonic deadline. Clocks may not move backward within the incarnation. Restart requires a fresh session ID and exchange under the original application authority and lifetime; it does not resume old keys or reset old replay decisions. Boot identity and the relationship between the supplied clocks, application intention and deadline must be enforced by the native owner.

Errors close the session and return a fixed refusal for ordinary exceptions. Interrupted control flow also closes it. Closure drops Python references to handshake, signing and record keys; it is not proof of memory zeroization. There is no rekey, ratchet, persisted session key or post-compromise recovery protocol.

## Receive modes and atomic handoff

The default `receive_mode='return'` permits `open()`, which commits DATA replay acceptance and returns the authenticated **sealed binary envelope**. Following it with a separate durable capture write can strand accepted data if the process fails between those commits. This return API does not qualify a durable private capture pipeline.

Opt-in `receive_mode='commit'` requires `counters.commit_receive` and permits `receive_into()` instead. Commit mode refuses `open()`; return mode refuses `receive_into()`. These are local constructor choices, not peer capability negotiation or proof of a remote storage policy.

After full key confirmation, DATA AEAD authentication, binary-envelope shape validation and original liveness checks, `receive_into()` supplies one frozen `ReceiveCandidate` to that same caller-owned provider. The candidate contains the full context, local role, preserved counter-claim binding and counter, handshake hash, outer-record hash, original monotonic deadline, observation times and sealed bytes. The sealed bytes are hidden in its representation. A candidate is a Python record, not an authority token or native attestation; the provider must independently bind the original capture UUID, boot identity, expected descriptor and private policy.

The provider must commit replay acceptance and a recoverable sealed capsule in one authoritative durable transaction. No separate DATA `record_receive` follows that call; confirmations retain their existing replay path. Only literal `True` followed by successful original liveness/ownership checks produces a successful `None` return, with no payload returned by Core. Any other result, exception, closure or interruption fences the session. A possibly committed capsule must be reconciled explicitly without resetting counters or needing the old session keys.

This generic seam includes no protected journal, SAGE adapter, private service-format admission or native provider. It cannot make independent storage writes atomic. After protected capture, the caller still must use the existing opener with independently pinned sender/recipient, verify the inner signature, enforce expiry and application replay, and complete native capture/consent admission before action. A session confirmation, joint quarantine commit or MT05 ACK is not proof of delivery, canonical application commit or permission to display the message.

## Review and evidence limits

The source review checked KK token order, prologue/pre-message hashing, transcript binding, directional split, record nonce/header authentication and commit ordering against the implementation. A checksum-pinned `noiseprotocol` 0.3.1 package was used only as a deterministic test oracle for both handshake bodies, the handshake hash and split keys. The current [reference fixture](../tests/fixtures/noise-kk-vector.json) is v2 and includes dedicated Noise statics; earlier v1 inputs remain historical. The oracle is not a runtime dependency or a security endorsement, and does not validate MPF2, the signature composition, native authority, secret destruction or RF behavior.

The [focused source controls](../tests/test_forward_session.py) cover known legacy-key substitutions in both roles, noncanonical/duplicate pins, wrong or missing local Noise keys before claim, absence of signing-private conversion, retired v1 claims, MPF1 refusal and changed Noise-pin rejection. Independent read-only checks matched the current v2 handshake bodies, transcript and split to the pinned oracle, completed both signed confirmations, and reproduced legacy-key, retired-claim and v1-framing refusals. These checks use public fixture keys and modeled authority, not native key generation or private transport.

Six [flow-composition source controls](../tests/test_forward_session_flow.py) passed carrying H1, H2, both confirmations and unchanged sealed DATA across two local frozen-flow/AEAD/journal hops; workers simulate `RF_DONE`. Link loss, corruption and replay recover. A relay with a valid changed second-hop descriptor still fails endpoint AEAD without advancing endpoint replay or refunding consumed cost. Normal adjacent grants share the original epoch expiry; fresh grants after expiry cannot renew endpoint authority. These are generic opaque benchmark carriers, not an admitted private service format, protected SAGE admission or native transport. They establish neither aggregate lifetime-cost qualification nor measured throughput. Caller confirmation ordering, loss handling and native lifecycle gates remain open.

Separate [receive-commit source controls](../tests/test_forward_receive_commit.py) use a real single-file SQLite fixture with modeled authority. They cover rollback between the replay/capsule inserts, lost returns after joint commit, duplicate refusal, mode/provider fences and post-commit closure, revocation, interruption and reentry. Independent checks reproduced both-or-neither persistence and recovery of committed sealed bytes after closing the sessions and dropping their key references. This validates the fixture transaction and generic callback ordering, not encrypted protected storage, an original private intention or native capture wiring.

The initial review found a callback fencing defect: `_live()` checked closure and ownership before invoking authorization/clock callbacks, but did not recheck those conditions after they returned. A source fixture closed the session inside its final clock callback and still obtained an authenticated outgoing record. Six closing-callback controls exposed four failures on that initial source.

The corrected source checks ownership and closure before and after both callbacks. An operation guard covers all public crypto operations; nested entry closes the session even when the callback catches the nested refusal. Constructor callbacks are guarded too, while `close()` remains available for cancellation. Focused source regressions now refuse closing callbacks, reentrant send/receive/handshake operations and interrupted sends, retaining committed nonce reservations and replay acceptance. Independent re-review reproduced refusal of the original final-clock case and a caught nested send, with the consumed counter retained. This resolves the demonstrated source defect; it does not qualify native lifecycle or secure memory erasure.

The v2 API removes the earlier direct reuse of converted signing private keys in the exchange. Native purpose separation and the full composition still need review: Noise cautions against using its static keys outside Noise without careful cross-protocol analysis, and libsodium recommends separate signing/encryption keys when possible. Matching a KK vector and rejecting the two known legacy keys do not prove that caller-supplied keys are independent or unused elsewhere. The dedicated statics, Ed25519 confirmation signatures, MPF2 record layer and legacy inner envelope must be reviewed together before production acceptance. [Noise security considerations](https://noiseprotocol.org/noise.html#security-considerations), [libsodium conversion guidance](https://doc.libsodium.org/advanced/ed25519-curve25519)

Remaining gates include independent cryptographic review; broader negative and interrupted-state coverage; native key generation, storage and erasure; durable claims and replay recovery; original policy/capture/consent integration; transport ordering and loss handling; and measured private transfer cost. Existing physical, firmware/source correspondence, third-party licensing, clean-history publication and [release-readiness](RELEASE_READINESS.md) gates remain open.

The competitive security goal is still a goal. Reticulum already documents forward-secret Links and optional destination ratchets; this experimental source does not establish stronger overall security or deployed forward secrecy. Performance evaluation continues to use our qualified measurements and published upstream figures, as described in the [comparison](COMPARISON.md#security-properties-and-gaps) and [roadmap](ROADMAP.md).

## Explicit record service admission

`MPF2.record` is a separate protected-message format in the generic radio and IP format maps. `inspect_record()` checks bounded header/kind/session/counter/length shape for H1, H2, both confirmations and DATA; it does not authenticate a record, attest native permission or admit its inner envelope. Every service transfer still binds the exact packet length and SHA-256. MPF2 must not be relabeled `LME.binary` or routed to the public runner.

Source controls cover all five encoded record kinds, malformed shapes, exact descriptor refusal before worker dispatch and refusal by the public application runner. These checks do not supply a native private stage coordinator. Consuming adapters must bind each phase/direction to the original application context and independently approved peers/Noise keys, preserve the original epoch and each host's monotonic deadline, and charge all forward/reverse flow, credit, ACK, retry and unknown-attempt costs against retained parent limits. Fresh child grants cannot renew that lifetime or reset debt. The legacy Lantern LME runner refuses this format until a dedicated stage adapter is supplied.
